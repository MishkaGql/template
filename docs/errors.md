# Архитектура обработки ошибок

## Назначение

Документ описывает единый стиль обработки ошибок для всех bounded context'ов и доменов сервиса. Цель - чтобы любой домен, столкнувшись с проблемой, отдавал клиенту ответ в формате **RFC 9457** единообразно и предсказуемо.

---

## 1. Контракт с клиентом: RFC 9457

Все домены и bounded context'ы отдают ошибки в формате Problem Details. Обязательные поля:

| Поле | Источник | Описание |
| :--- | :--- | :--- |
| `code` | **Домен / Инфра** |  «что пошло не так». Машино-читаемый идентификатор. |
| `detail` | **Домен / Инфра** | Человеко-читаемое сообщение с учётом контекста. Опционально. |
| `title` | Handler (маппинг) | Общий заголовок ошибки. Фиксирован на code. |
| `type` | Handler (маппинг) | URI, идентифицирующий тип проблемы. Фиксирован на code. |
| `status` | Handler (маппинг) | HTTP-статус. Фиксирован на code. |
| `instance` | Handler (runtime) | Уникальный идентификатор конкретного инцидента. |

> **Уровни ответственности:** `code` и `detail` - это сердце домена и инфры, именно они несут бизнес-смысл и уходят клиенту. Писать туда "connection refused" запрещено. Остальные поля - это маппинг, который живёт в handler.

### 1.1. Про `code`

- Это **тег**, а не человекочитаемое сообщение.
- Коды не обязаны быть общими: `invalid_request` и `trip_not_found` одинаково легитимны.
- Разделять их на «разные виды кодов» не нужно - код всегда несёт одну семантику: «что пошло не так».

### 1.2. Про `detail`

- Опциональное сообщение, которое учитывает контекст (конкретный ID, имя сущности и т.п.).
- Фиксированные `title` часто слишком общие, поэтому `detail` даёт конкретику.
- По умолчанию **всегда ставьте `detail`**. Решение убрать его - это вопрос code review и принимается, только если `code` + `title` исчерпывающе описывают проблему.

### 1.3. Где хранить коды

- Каждый `code` фиксируется в том **domain** или **bounded context**, где он переиспользуется.
- Предпочтительное место - **domain** (ближе к месту возникновения).
- Копирование кодов между модулями допустимо - это избавляет от постоянной беготни между папками.
- Выносить в bounded context или shared kernel можно в исключительных случаях, когда одинаковых кодов действительно много (**7-10+**). Звучит как редкий кейс, но оговорить его стоит.

## 2. Интерфейс `AbstractError`

Чтобы все домены придерживались единого стиля ошибок (опциональный `detail`, фиксированный `title`), введён общий интерфейс. Любой домен, который хочет сделать кастомный тип ошибки, обязан его реализовать.

```go
type ErrorCode string

type AbstractError interface {
    error
    Code() ErrorCode
    Message() *string // detail
}
```

### Зачем `Message()` в интерфейсе, если `detail` опционален?

3 причины:

1. **Явность.** На этапе MVP, если в интерфейсе не будет `Message()`, а другому микросервису `detail` понадобится - ему придётся писать свою структуру, реализовывать свои методы + ещё и обязательные. `AbstractError` в таком случае теряет смысл как общий контракт.
2. **Совместимость с JSON.** `Detail` в Problem Details обязан прокидываться в JSON. Если он `nil`, сериализатор просто не выведет поле (`omitempty`). Но метод то обязан существовать в каком-то виде - даже если возвращает `nil`.
3. **Явная декларация.** Реализуя, например, `NotFoundError`, вы явно указываете в `Message()`, что он возвращает `nil`. Это читаемее, чем отсутствие метода.

### Доступ к полям

Все поля структур закрыты. Доступ - только через методы. Такое решение связано с тем, что эти ошибки живут в shared kernel, который шарится между всеми контекстами и давать доступ к полям - значит увеличить шанс не правлиьного использования, что поведет за собой много неприятных багов

## 3. `ServiceError` (Shared Kernel)

Shared kernel предоставляет стандартную реализацию `AbstractError`, которую могут использовать все домены без написания своих структур.

```go
Общий пример

type ServiceError struct {
    code    ErrorCode
    message string  // НЕ указатель. Пустая строка = нет detail.
    cause   error
}

// Реализация AbstractError
func (e *ServiceError) Code() ErrorCode { return e.code }

func (e *ServiceError) Message() *string {
    if e.message == "" {
        return nil
    }
    return &e.message
}

func (e *ServiceError) Error() string { /* склейка code + message + cause */ }
func (e *ServiceError) Unwrap() error { return e.cause }
```

> **`message` - это `string`, а не `*string`.** Если контекст не нужен, пишется `""`. Handler подхватывает это и отдаёт клиенту `nil` как указатель (через `omitempty` в JSON). Внутри сервиса работать с обычной строкой удобнее, чем с указателем.

## 4. Поле `cause`: смысл и правила

`cause` определяет **причину** того, из-за чего произошла ошибка. Это замена `fmt.Errorf("...: %w", err)` на уровне структур.

### Что может лежать в `cause`

| Тип | Пример | Комментарий |
| :--- | :--- | :--- |
| Техническая ошибка | `pgx.ErrNoRows`, `context.DeadlineExceeded` | Сбой инфраструктуры |
| Другая `AbstractError` | Вложенная `ServiceError` с **другим** кодом | Трансляция ошибок между слоями |

### Как их отличать

- **Технические ошибки** - ищутся через `errors.Is` / `errors.As` с конкретным типом (`errors.Is(err, context.DeadlineExceeded)`).
- **Абстрактные (сервисные) ошибки** - ищутся по `Code()`, потому что тип у всех `ServiceError` одинаковый.

### Инварианты `cause`

1. **Handler обязан получить `ServiceError` в первом звене цепочки.** Он не должен стучаться в `cause` и искать её в недрах ада.
2. **В `cause` не должно быть двух `ServiceError` с одинаковым кодом.** Звучит странно: «причина того, что юзер не найден - юзер не найден». Это тавтология, нарушающая семантику причинно-следственной связи.
3. **`ServiceError` не должен переопределять `ServiceError` с таким же кодом.** Иначе причиной становится не код, а сообщение - это ломает идею кода как тега «что пошло не так».

### Паттерн принятия решений

Если вы не уверены, не переопределите ли случайно `ServiceError` с таким же кодом:

1. Выкидывайте ошибку через `fmt.Errorf("контекст: %w", err)` — для добавления контекста в логи.
2. Либо используйте **другой** `code` (трансляция).
3. И только когда окончательно убедились в корректности — врапьте в `ServiceError`.

## 5. Маппинг в handler'е

В каждом handler'е (или в центральном error-handling middleware) должно быть определено соответствие `code → (title, type, status)`.

```go
Общий пример

func toProblem(err error) Problem {
    var abs AbstractError
    if !errors.As(err, &abs) {
        // Не AbstractError — fallback на internal_error
        return Problem{
            Type:   strPtr("about:blank"),
            Title:  strPtr("Internal Server Error"),
            Status: 500,
        }
    }

    return Problem{
        Code:     string(abs.Code()),
        Detail:   abs.Message(),                     // может быть nil
        Title:    strPtr(titleByCode(abs.Code())),   // из маппинга
        Type:     strPtr(typeByCode(abs.Code())),    // из маппинга
        Status:   statusByCode(abs.Code()),          // из маппинга
        Instance: strPtr(traceIDFromContext(ctx)),   // runtime
    }
}
```

Handler берёт **верхнюю** ошибку из цепочки. Он не должен обходить `cause` в поисках «настоящего» кода - если верхний слой уже сформировал `ServiceError`, это и есть контракт.

## Примеры

| Хочу… | Делаю |
| :--- | :--- |
| Отдать клиенту новую бизнес-ошибку | `NewServiceError(code, message, cause)` |
| Добавить контекст в логи, но не менять контракт | `fmt.Errorf("ctx: %w", err)` |
| Пробросить ошибку без изменений | `return err` |
| Сменить смысл ошибки для клиента | `NewServiceError` с **новым** кодом, старая в `cause` |
| Уточнить формулировку для клиента (тот же смысл) | **Запрещено** через вложение. новый код   |
| Найти в цепочке техническую ошибку | `errors.Is(err, target)` |
| Найти в цепочке `ServiceError` по коду | Кастомный метод с поиском по code         |
