# Правила именования тест-кейсов в Go

Все тестовые функции должны именоваться в соответствии со строгим форматом, отражающим главную цель проверки.

## Тесты

Сначала тесты -> тестовые данные var, const распологаем вверху файла,
функции вспомогательные для создания обьекта -> после всеъ тестовых файлов


## Шаблон названия
Test{Имя}{ЧтоБудет}{ПочемуБудет}

---

## 1. {Имя}
* **Правило:** Имя должно отражать главную суть проверки.
* **Исключение избыточности:** Если из названия файла или пакета очевидно, с какой сущностью происходит работа (например, сущность `trip`), дублировать её в названии теста не нужно.
* **Пример:** Вместо `TestTripCreate`  пишем `TestCreate`.

---

## 2. {ЧтоБудет}
Отражает ожидаемый результат работы функции.

* **Код ошибки/ответа (основной вариант):** Формат `Code{НазваниеКода}`.
  * *Пример:* `CodeNotFound`
* **Тип ошибки (если важен тип):** Формат `Err{НазваниеОшибки}`.
  * *Пример:* `ErrNotFound`
* **Крайние случаи (важны и тип, и код):** Соединяются через двойное подчеркивание `__` в порядке **[Тип]_[Код]**.
  * *Пример:* `ErrNotFound_CodeNotFound`

---

## 3. {ПочемуБудет}
Отражает входные данные или условия, которые приводят к ожидаемому результату.

* **Корректные данные:** `CorrectData`
* **Конкретный ID:** `CorrectId`
* **Любой подходящий ID (если конкретное значение не важно):** `CorrectAnyId`

---

## Принцип главной проверки

Название теста всегда отвечает **только за суть и главную цель проверки**, а не за побочные действия или сопутствующие ассерты.

* **Пример с завершением поездки:**
  * **Главная проверка (суть теста):** Статус поездки успешно изменился на `completed`. Название теста строится вокруг этого события.
  * **Побочные проверки:** Получение данных завершенной поездки, сравнение ID, проверка дат и других полей. Эти действия важны и должны быть в теле теста, но они являются следствием успешного выполнения главного действия и **не выносятся** в название. Соответственно, все тесты именуются в соответствии с главной проверкой.
